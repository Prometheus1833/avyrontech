## Security posture confirmed in the dashboards

- Cloudflare zone `avyron.ro` is on the Free plan. SSL/TLS is **Full (strict)**; **Always Use HTTPS** and **TLS 1.3** are enabled, and minimum TLS is **1.2**. HSTS is not enabled. HSTS requires a rollout review because browsers cache it and an incorrect policy can make the site inaccessible; do not toggle it as a routine setting.
- One custom WAF rule of five Free slots is active and blocks unsafe methods and scanner paths. The sole Free rate limiting slot is occupied by an active rule named **Leaked credential check**, matching `cf.waf.credential_check.password_leaked`, threshold 5 requests/10 seconds by IP and 10-second block. It does **not** impose a general rate limit on logo generation, domain lookups, uploads or authentication. Changing it would replace existing protection and can affect legitimate users. Cloudflare's Free Managed Ruleset is deployed by default according to Cloudflare documentation; the dashboard's "No Managed rules created" does not prove it is absent.
- GitHub reports `main protected=false` and an empty repository ruleset list. The connected GitHub identity has `push=true` but `admin=false` and `maintain=false`; querying Actions policy returned 403, and security alerts endpoints returned 404. Thus branch protection, Actions policy, Dependabot alerts and secret scanning cannot be verified or activated using this identity. Public-repository rulesets are available on GitHub Free, but managing them requires admin or the custom rule permission.
- The existing CI on `main` has `permissions: contents: read`, typecheck, lint, D1 audit, builds and tests. The expanded security CI, dependency fixes, public abuse limits, authorization fixes, platform owner roles and upload scan gate remain in separate open PRs #66-#70. Their green checks or previews do not make them active in production. Administrative MFA remains deferred by owner instruction.
- Cloudflare Security Overview showed an older DMARC insight. This audit could not independently query DNS from the restricted terminal; treat it as **suspected / requires live DNS verification**, not a confirmed current DNS fault.

## Exact, approval-gated synchronization order

1. **Preview resource creation (Cloudflare account Avyron, Workers Free):** after approval for these two named resources, create `avyron-async-jobs-preview` and `avyron-async-jobs-preview-dlq` with `wrangler queues create <name>` or in dashboard. Confirm both appear in `wrangler queues list`. Do not attach a production consumer to either. Rollback: remove only the two empty newly created preview queues after confirming no messages or consumer; never touch production queues.
2. **Preview D1 migrations:** after separate approval for migration of `avyron-db-preview`, first read its current migration history and a Time Travel bookmark without publishing it. Apply the pending migrations using `wrangler d1 migrations apply avyron-db-preview --remote --env preview --config wrangler.jsonc`. Confirm ordered history through `0072`, run `PRAGMA foreign_key_check` and `PRAGMA quick_check`, then test preview with synthetic data. This changes remote schema and may be resource-intensive; review the 48 migration files and expected row counts before execution. Rollback: use the recorded D1 Time Travel bookmark only after checking intervening writes and impact; a point-in-time restore can lose new data. Production D1 is already at `0072`; PR #70 adds `0073` and needs its own release approval.
3. **Preview Worker:** after the resources and migrations pass, review the exact preview binding names, secrets' **presence only**, routes and schedules. Then request explicit approval for `npm run deploy:api:preview`, which uploads a remote Worker version. Verify its version, health, Queue producer/consumer binding, email disabled behavior and representative authenticated/public flows in the authorized test environment. Rollback to previous preview version if needed; do not point preview at production D1/KV/R2/Queues.
4. **R2 metadata access:** use an account administrator to grant a dedicated, short-lived **read-only account-level R2 metadata** token for the AVYRON buckets. An object-scoped S3 token does not authorize the R2 REST bucket metadata endpoint. Never place the token in this repository, PR, logs or report. Recheck bucket public access, lifecycle, lock and logging through the API; revoke the temporary token after verification. Enabling Data Access Logs requires a separate cost/retention review: Cloudflare documents seven-day retention and an Observability pricing change from 1 December 2026. Establish and test an R2 backup before claiming recovery readiness.
5. **Zone WAF and TLS:** prepare a proposed rule with exact paths, thresholds and bypasses based on sampled security analytics; review normal traffic before replacing the occupied Free rate-limit slot. Keep the credential leak rule until an equivalent protection exists. Prepare any HSTS, DMARC or DNS adjustment with a rollback plan and explicit approval for the exact production change. Do not use a paid add-on or upgrade silently.
6. **GitHub administration:** an administrator of `Prometheus1833/avyrontech` should enable a `main` ruleset requiring pull requests, at least one independent review, the stable `build-and-test` check, and block force pushes/deletion; test on a harmless PR before relying on it. Review default Actions permissions, retain `contents: read` for CI, enable dependency graph/Dependabot alerts and public-repository secret scanning/push protection where available, then verify each setting through GitHub UI/API. Rollback a too-strict ruleset by disabling it temporarily, recording the reason and re-enabling after correction. Do not merge the open security PRs without review; deployment remains separate.

## Verification and limits

Read-only service checks: `git fetch origin main`, GitHub API for repo/branch/rulesets/Actions, Wrangler D1 lists and migration-history queries, Wrangler Queue list, and Cloudflare dashboard for Workers, D1/KV/R2/Queues/WAF/TLS/plan. Two single, nondestructive public GET checks returned HTTP 200: `/` in 0.443 seconds and `/api/health` in 0.100 seconds from this client. These are availability snapshots, not a performance baseline or proof of every integration. Only the task branch and PR were written remotely; no Cloudflare resource, GitHub security setting, production code, D1 data, DNS or WAF configuration was changed. No deploy, provider activation, active adversarial production probe or data restore was performed. Performance impact is **not measured** because no runtime change was applied; projected extra preview Queue operations and D1 migration work must be measured in the approved test run. User traffic can be affected by WAF/HSTS changes, so baseline and rollback checks are mandatory. Recheck all observations immediately before any approval-gated operation.
