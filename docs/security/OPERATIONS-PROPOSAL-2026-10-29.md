## Cloudflare WAF and rate limits

The repository routes API traffic through the Worker on `avyron.ro`, `www.avyron.ro`, `api.avyron.ro`, `app.avyron.ro`, and `surveys.avyron.ro`. A read-only dashboard check on 29 October confirmed the `avyron.ro` zone is on Free: one of five custom-rule slots is used by an active Block rule for unsafe methods/scanner probes, and the sole edge rate-limit slot is used by an active Block rule for leaked credentials. No managed rule was created in the displayed list; Cloudflare default protection is shown. Other zones and the effect on legitimate traffic were not audited. The Worker already limits login to 20 attempts/IP and 8 attempts/identifier per 15 minutes, and uses a separate rate-limit binding. After exact approval and a traffic baseline:

1. In the matching zone's **Security → WAF**, record existing rule IDs, order, action, skip rules and recent baseline. If the plan offers a nonblocking Log action, stage a rule for `http.request.method eq "POST"` and `http.request.uri.path in {"/api/auth/login" "/api/auth/mfa/challenge" "/api/auth/forgot" "/api/auth/reset"}` on the five hosts above. Keep payment and email webhooks outside this rule. Observe seven days of requests, country/network distribution, false positives and Worker 429s.
2. The Free edge rate-limit slot is occupied. Do not replace the leaked-credential rule without an exact decision. If a separate edge limit becomes available and the measured legitimate peak permits it, propose a login rule keyed by source IP at 60 requests per 15 minutes, initially in log/simulate mode if supported. This is an upper bound above the Worker gate, intended to reduce upstream volume; do not enable a block/challenge action until the traffic owner approves the measured threshold and accessibility impact. For uploads, use a separate rule with route-specific baselines. Do not challenge signed provider webhooks.
3. Verify with benign synthetic requests in preview first and passive production telemetry after an approved change. Record rule ID and timestamp. Compare 429/challenge rate, successful login, checkout and support contact completion against the pre-change baseline. Estimated effect in log mode: no request blocking; enforcement effect cannot be estimated credibly without the seven-day baseline. Rollback: disable only the new rule and verify the previous error and completion rates recover.
