### 4. R2 backup, access logs and recovery

Use a separate backup destination and read-only source export credentials with least privilege for the S3 object API. Before implementation, choose retention, region, encryption key owner, schedule, recovery point/time objectives and budget. Keep source and backup credentials separate; test an isolated restore and hash/size comparison of synthetic objects before scheduling. Bucket lock only prevents deletion/overwrite and may break application cleanup, so do not enable it as a backup substitute. Account-level R2 REST bucket metadata requires Admin Read only / Workers R2 Storage Read permission; object-scoped R2 tokens are only for the S3 API. Dashboard access already allows the present read-only inventory, so no new token is required solely for this report.

After the destination is approved, the storage administrator should: (a) create a non-public backup bucket under a separate security boundary; (b) issue an Object Read only S3 credential scoped to each source bucket and a separate Object Read & Write credential scoped only to the backup destination, with expiry and vault ownership; (c) configure two `rclone` S3 remotes outside the repository using the correct R2 account/jurisdiction endpoints; (d) dry-run a dated-prefix copy for each bucket, then run the copy only after approval; (e) compare object counts and sizes and run `rclone check` without publishing object names; (f) restore a synthetic object into an isolated bucket and compare its digest; (g) record recovery time and schedule retention/alerts. Do not use destructive `sync` from source to backup until deletion behavior and retention are explicitly approved. [Cloudflare's S3 setup](https://developers.cloudflare.com/r2/get-started/s3/), [CLI guidance](https://developers.cloudflare.com/r2/get-started/cli/) and [token scopes](https://developers.cloudflare.com/r2/api/tokens/) describe the supported interfaces.

Data Access Logs are currently disabled. If approved, enable them on the two production buckets, note the start time, verify object-operation events in Workers Observability using synthetic operations, and set an owner to review delete/write anomalies. Logs are best effort, omit failures with status 400+, have seven-day retention and become billable through Observability on 1 December 2026; they are not a backup or a complete audit log. Rollback: disable only Data Access Logs and verify cost and event volume stop after propagation. R2 Event Notifications require Workers Paid on the observed account.
